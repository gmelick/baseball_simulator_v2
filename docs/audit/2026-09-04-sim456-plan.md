## 1. What the defect was

`derived.pitcher_season_metrics.whiff_rate` counted `type = 'C'` over all
pitches. Code `C` is a called strike. The batter never swung. The column held
the called-strike rate (~16%) under the name "whiff". It is one of the seven
`COMMAND_FEATURES` in the pitcher engine, so swing-and-miss ability was absent
from the engine while a feature named for it measured something else.

## 4. Two residuals the trace found

### 4a. The batter platoon z-swing legs are still inverted (NEW — file as SIM-522)

The SIM-501 re-land fixed `z_swing_rate` at the season level. The two platoon
legs did not get the fix. `player_profile_computor.py` lines ~2196 and ~2235
still count `type IN (NON_SWING)` for `z_swing_rate_vs_l` and
`z_swing_rate_vs_r`, so both hold the z-TAKE rate.

Live proof (qualified batters, 2024): `z_swing_rate` **0.680**, `z_swing_rate_vs_l`
**0.323**, `z_swing_rate_vs_r` **0.321**. The legs sum with the season column to ~1.0.

Consumers: `batter_similarity.py` lines 935–936 put the legs into
`platoon_vs_l_vec` / `platoon_vs_r_vec`; the batter sub-calibrator reads
`z_swing_rate_vs_r` for its sigma fit.

Effect on the engine today: **none on the scores.** The inversion is `x → 1 − x`.
It preserves every pairwise difference, and the RBF sub-score sees only differences
after z-scoring. The calibration sigma sees only the spread, which is identical.
So the batter similarity output is numerically unchanged by the mislabel.

Why fix it anyway: the column lies to every direct reader (the Data Lab SQL
console, the AI assistant, any future feature that compares the season column with
its platoon legs), and the next person to add a swing-vs-take delta reads it
backwards. The fix is `IN` → `NOT IN` on two lines. It is inert until the next
profile recompute, like all profile SQL.

Plan for SIM-522 (XS):
1. Change the two predicates to `type NOT IN (NON_SWING)`; state the defect at the site.
2. Extend `test_sim501_profile_code_sets.py`: assert the source contains no
   `zone BETWEEN 1 AND 9 AND type IN ('B', 'C', 'H', 'P', '*B')` predicate feeding
   a `z_swing` column.
3. Ride the next scheduled recompute (SIM-517 needs a pitch-pool rebuild with
   `catcher_id`; SIM-518 owns the shared rebuild). Do NOT start a recompute for this.
4. After that recompute, verify: `AVG(z_swing_rate_vs_l)` ≈ `AVG(z_swing_rate)` ≈ 0.67.

### 4b. `csw_rate` and `whiff_rate` overlap in the command sub-score (D-N7 — a decision, not a defect)

The 2026-07-23 adversarial review predicted the fix would make `csw_rate` and
`whiff_rate` exactly collinear. It did not, because the landed whiff is per SWING
while csw is per PITCH. Measured on the live 2024–2025 profiles: corr(csw, whiff)
= 0.73–0.79; corr(k_rate, whiff) = 0.74–0.77. The command RBF weights all seven
z-scored features equally, so swing-and-miss now enters the sub-score through three
correlated features (k_rate, csw_rate, whiff_rate).

Recommendation: leave `COMMAND_FEATURES` alone in this close. A feature swap
(`csw_rate` → a called-strike-only rate) is an engine change that needs a
`sigma_command` refit, a `pitcher_sim` re-export (~1 h) and a regression-fixture
regen, and its value is only measurable on the pitcher K prop. That is SIM-429's
calibration-refit work. Record the measurement on SIM-429 so it is tested there,
once, against the K-prop ECE.
