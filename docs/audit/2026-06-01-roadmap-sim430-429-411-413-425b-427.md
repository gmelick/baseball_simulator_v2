## SIM-430 — full-pool `/simulate` throughput (fan-out / OOM)

### DONE this session — the per-worker `pitcher_sim` dict OOM driver is eliminated
**Root cause (measured, corrects the design doc):** the OOM was NOT the object-dtype
`outcome_type`/`event` arrays (~15 MB). It was `EngineArtifacts.pitcher_sim`, a
dict-of-dicts (1677 outer × ~3574 inner = 6.0M `{str:float}` entries) costing **~2.0 GB
resident per process** and NOT shareable through `multiprocessing.shared_memory`, so
every worker held a full private copy.

**Fix (shipped):** `build_pitcher_sim_matrix` now also writes a dense
`(n_prof × n_prof)` float32 `pitcher_sim_matrix` (1677² = **11.2 MB**, 60.3% nonzero)
into `pitcher_sim.npz`; `EngineArtifacts.load` reads it and **skips the ~2 GB dict
parse** entirely (dict kept only as a legacy fallback); it rides the existing SIM-403b
shared-memory seam (`extract_shared_arrays`/`attach_shared_views` → `pitcher_sim.matrix`)
so all workers attach ONE read-only view; `FullPoolSampler._f_pitcher` reads a
contiguous row instead of scattering the dict — **byte-identical** draws (8 unit tests,
incl. a full draw-sequence equivalence).

**Live-verified:** an isolated worker-path load dropped from **2364 MB → 367 MB** with
`len(pitcher_sim) == 0` (dict skipped) and the 11.2 MB matrix present; the serving
parent dropped from ~2.4 GB → **270 MB**; boot now publishes **42** shared arrays
(176.9 MB, +1/+11 MB = the matrix). The live `/data/.../pitcher_sim.npz` was densified
in-place (minutes, no engine re-run) and the app restarted onto the matrix path.

### STILL OPEN — the SLA / worker-scaling half. Deep profiling (2026-06-01) narrowed it sharply.
Raising `SIM_RUNNER_WORKERS` is still not safe on this host. The prewarmed ProcessPool
worker measures **~6.4 GB private-anon** RSS (two ~1.5 GB regions). A bisecting profiling
pass established **where it is NOT** and **where it is**:

- **RSS bisect:** the worker is **already ~5974 MB at `_worker_init` *entry*** — i.e.
  BEFORE any of our code runs (the segment attach then adds only ~2 MB, and the
  load+warm only ~400 MB). So the 6 GB is allocated during the **spawn bootstrap**, not
  the load/warm path.
- **C/numpy, not Python:** with a `tracemalloc` snapshot taken inside warm, only
  **368 MB** is Python-tracked while RSS is 6.5 GB → the bulk is C/numpy/buffer memory,
  not Python objects.
- **Ruled OUT:** the `pitcher_sim` dict (parent is 270 MB, dict-skip proven); glibc
  arenas (`MALLOC_ARENA_MAX=2` made no difference); `uvicorn --reload` (workers=2 with
  `--reload` removed still ~6 GB each); `production_machine_factory` (builds only the
  ~470 MB sampler, not the engines); `build_all_engines` at import (it runs in the
  lifespan, line 198, not in `create_app()`); and any module-level heavy load in
  `simulation/` or `similarity/` (grep: none).
- **A plain `spawn` child** (raw `mp.Process` importing the sim modules + warming) is
  only **467 MB** — so it is NOT the sim import chain. The 6 GB is specific to a
  ProcessPoolExecutor worker spawned **from the loaded uvicorn app process**.

**Net hypothesis:** each spawn pool worker re-loads ~6 GB of C/numpy at bootstrap that it
does NOT need (a full-pool worker needs only the ~470 MB bundle) — the cause is in the
`ProcessPoolExecutor(spawn)` bootstrap from the engine-loaded parent, not in our load/warm
code. **The exact source is not yet named.**

**⚠ Safety lesson (do NOT repeat):** `PYTHONTRACEMALLOC=1` to trace it from interpreter
start was a mistake — tracemalloc stores a traceback per allocation across the multi-GB
engine build, ballooning the app process and pressuring host RAM until **Docker Desktop's
engine wedged (all `docker` calls 500'd)**; recovery needed a Docker Desktop restart. Do
not run interpreter-wide tracemalloc on the live multi-GB boot.

**Safe next steps (NOT on this shared 16 GB host concurrently with the app):**
1. On a **dedicated host** (or with the live app stopped): reproduce with a memory-capped
   container (`docker run --memory=…`) so any balloon is cgroup-contained, then name the
   6 GB with **memray** or a `py-spy`/`gdb` heap inspection (needs `cap_add: [SYS_PTRACE]`).
2. Likely-fruitful code probe: instrument the `ProcessPoolExecutor` creation +
   `multiprocessing.spawn` bootstrap to see what the worker imports/unpickles (check the
   pool's `mp_context`, the pickled task/initargs closure, and whether the spawn re-import
   of the main module pulls in a heavy path).
3. If the worker genuinely only needs the ~470 MB bundle, the fix is to ensure the worker
   bootstrap imports the **minimal** module set (decouple the task module from the
   engine-heavy imports) so it never materialises the 6 GB. Only then raise
   `SIM_RUNNER_WORKERS` and hard-gate the n=100 < 30 s SLA.

`SIM_RUNNER_WORKERS` left at **1**; all profiling instrumentation + debug env reverted.

### ✅ RESOLVED 2026-06-02 — it was fork-COW-defeat; fix = forkserver
The root cause was named by confirming the pool's start method: a no-`mp_context`
`ProcessPoolExecutor` here reports **`fork`** (the worker's cmdline is the parent's, not
`spawn_main`). So each worker COW-**forks** from the ~6 GB engine-loaded parent, and CPython's
refcounting + cyclic GC write to every inherited object header → **copy-on-write is defeated** →
each worker materialises ~6 GB it doesn't need. This explains every earlier clue: `tracemalloc`
(started in the worker) saw only 368 MB because the 6 GB was allocated in the **parent**, pre-fork;
the 467 MB "spawn child" was forked from a *lean* parent; `MALLOC_ARENA_MAX`/`--reload` were
irrelevant. (The `spawn_main` PID seen earlier was a Manager/forkserver helper, not the pool worker.)

**Fix (shipped):** `BatchRunner._pool_kwargs` passes `mp_context=forkserver` (env-overridable via
`SIM_MP_START_METHOD`) — workers fork from a clean ~30 MB server, never inheriting the engines — plus
a **`mem_limit: 10g`** cgroup cap on the `app` service so a runaway is contained to the container,
never the host. **Measured live:** pool workers **~6 GB → 373 MB each** (16×); app healthy at 8
workers / 8.4 GiB; **n=100 `/simulate` 215 s → ~38 s (5.6×)**, no OOM. `SIM_RUNNER_WORKERS=6` (8 gave
no gain). **Remaining:** the 30 s SLA is NOT met — throughput plateaus past ~6 workers (a serial
parent-side result-handling / per-game-rebuild bottleneck), which is the SIM-430 "per-game cost"
work, distinct from the (now-resolved) worker-memory issue. +4 tests (`test_sim430_forkserver.py`).
⚠ `PYTHONTRACEMALLOC=1` on the live boot wedged Docker Desktop during diagnosis (reverted; `mem_limit`
now makes that impossible) — use memray/py-spy in a capped container, never live interpreter-wide
tracemalloc.

## SIM-429 — calibration quality (partially implementable now)

**(1) Pitcher K/BB PMF over-prediction — root cause found, fix is code-only.** The
SIM-432 validate run found K@5.5 ECE 0.52 (pred_over 0.86 vs obs 0.35), BB@1.5 ECE 0.39,
PMF coverage K 0.41 / BB 0.60 (too narrow). NOT a PMF-builder bug — `prop_distributions`
builds them correctly. The cause: **the starter is never pulled** in production —
`production_machine_factory` builds `StateMachine` with `manager=None`, so
`_maybe_pull_starter` early-returns and one pitcher accrues ~38 BF / ~9 IP every game
(K mean ~2×, tiny variance). This is the SAME root as SIM-427 + a latent bug
(`GameState.pitcher_pitch_count` is **never incremented** in `step_pitch`, so the pull
gate can't fire even when wired). Fix (now): increment the pitch count + wire a default
manager with a generic bullpen into `production_machine_factory` so the starter is
pulled at a realistic workload. **Risk:** changes every game's distribution (W/L/S, ER,
win-prob) → regenerate regression golden fixtures + validate with `sim_stats.py` at
≥400 sims/game; gate behind `SIM_MANAGER=1` (mirror `SIM_FULL_POOL`).

**(2) Runs ~10-12% low — per-channel tuning (now, but iterative).** NOT the global
`SIM_RUN_CALIB` (intentionally neutral). Levers: `_EXTRA_ADVANCE_P` (sim_loop.py:1328-32),
ground-out/fly-out scoring rates, and stronger RISP conditioning in
`FullPoolSampler.battedball_new_pa` (currently soft, `sit_sigma=2.0`). Requires measured
sweeps at ≥400 sims/game reading the per-channel/RISP breakouts — not a one-shot diff.

**(3) Fuller win-prob curve — throughput-gated (SIM-430).** `validate_props` replays N
iters/game serially at ~2.2 s/iter (1 worker). A full-season fit (~2,470 games × 50 ≈
75 h) is impractical until SIM-430's fan-out lands. Interim: a bounded ~600-game/30-iter
overnight fit (~11 h) is runnable today via `--write-calibration`.

**(4) CLV backtest — BLOCKED (no odds).** `raw.game_odds` and `raw.prop_odds` are **empty**
(0 rows). Only `MockOddsAPI` + the live BettingPros provider (current/opening lines, no
historical-closing backfill) exist. A real CLV backtest needs entry+closing lines for
completed games → external historical-odds feed OR forward-capture closing lines on
upcoming games (SIM-340 marking). Only a synthetic-line smoke is possible now.
