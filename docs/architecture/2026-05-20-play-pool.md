# Play-Pool Architecture (Phase 3)

*Ticket: SIM-300 · Owners: Backend Developer + ML Engineer · PM-authored · Date: 2026-05-20*
*Status: ACTIVE — reconstructed 2026-05-20 after the original was lost to OneDrive
truncation (see `docs/HANDOFF_PHASE3.md` §7). This is the load-bearing contract for
SIM-301 (nightly cache serializer) and SIM-302 (PlayPoolSampler API).*

---

## 0. Purpose

Phase 2 produced 11 similarity engines that answer *"which historical players /
pitches / batted balls are most like this one?"* Phase 4's simulation loop will,
for every plate appearance and every pitch, need to **sample a concrete historical
outcome** from the pool of plays that are similar to the current matchup — fast
enough to simulate a full game in < 2 s and 100 games in < 30 s (the SLA the
Performance Engineer owns).

Doing the similarity query + candidate gather + sampling live, per pitch, is too
slow. The **play pool** is the precomputed bridge: a disk-materialized, pre-filtered
set of FAISS indexes ("tiles") plus their backing outcome rows, built nightly, that
the simulation runner hot-loads at startup and samples from in O(k) per pitch.

This document defines five contracts:

1. The **pre-filter contract** — how the candidate space is narrowed before any
   FAISS search runs (§3).
2. **Sub-index materialization** — how tiles are sharded, named, and serialized to
   disk (§4).
3. The **recency lifecycle** — how the last-two-seasons recency boost is kept fresh
   (§5).
4. The **`PlayPoolSampler` API** — the four-method surface the sim loop calls (§6).
5. The **performance / RAM budget** — the ≤ 2 GB envelope and how it is enforced
   (§7).

## 1. Where this sits in the architecture

```
derived.* (Postgres)  ──nightly──▶  DuckDB (sim.pitch_pool, sim.outcome_pool, similarity_profiles)
                                          │
                       SIM-301: pipeline/batch/play_pool_cache.py   (this is the BUILD side)
                                          │  writes tiles to /data/play_pool/...
                                          ▼
                            /data/play_pool/<season>/<pitcher_id>/<bat_hand>.faiss  (+ .meta, + .npy)
                                          │
                       SIM-302: simulation/play_pool_sampler.py     (this is the READ side)
                                          │  hot-loads tiles, serves k-NN samples
                                          ▼
                            Phase 4 simulation loop (SIM-303 wires it in)
```

The build side (SIM-301) is a nightly batch job that runs **after**
`pipeline/batch/player_profile_computor.py`. The read side (SIM-302) is a library
imported by the simulation runner; it never touches Postgres and only reads the
materialized tiles + DuckDB outcome rows.

## 2. Terminology

- **Tile** — one serialized FAISS index plus its sidecar files, scoped to a single
  `(season, pitcher_id, bat_hand)` triple for the pitch pool, or `(season, bat_hand)`
  for the batted-ball pool. A tile is the unit of build, cache, load, and eviction.
- **Fingerprint** — the float vector indexed in FAISS. Pitch fingerprint is the
  10-dim vector from the pitch-to-pitch engine (SIM-041); batted-ball fingerprint is
  the 3-dim launch vector from the batted-ball engine (SIM-042).
- **Outcome row** — the actual historical result a sampled fingerprint maps back to
  (pitch result, or batted-ball event with bases/outs deltas). Lives in
  `sim.pitch_pool` / `sim.outcome_pool` in DuckDB; the tile stores the *row ids* so
  the sampler can fetch the payload.
- **Recency boost** — duplicating last-`RECENCY_BOOST_SEASONS` rows once in the index
  so recent plays are ~2× as likely to be sampled (production default ON, see §5 and
  the existing `RECENCY_BOOST_SEASONS=2` constant in the FAISS engines).

## 3. The pre-filter contract

Pre-filtering is what makes per-pitch sampling cheap: instead of searching all ~1M
pooled pitches, the sampler searches only the tile that already matches the matchup's
hard constraints. **Each engine pre-filters by exactly the dimensions that are
load-bearing for that engine and no more** — over-filtering shrinks the pool below
the reliability floor; under-filtering wastes RAM and dilutes signal.

| Pool | Pre-filter key | Rationale |
|---|---|---|
| **Pitch-to-pitch** (SIM-041) | `pitcher_id` + `bat_hand` | A pitch's geometry is a property of *who threw it to which-handed batter*. Cross-pitcher or cross-hand sampling would fabricate arsenals. Handedness is a hard split here (consistent with the pitcher engine's hard L/R partition, HANDOFF §4). |
| **Batted-ball** (SIM-042) | `bat_hand` only | Launch geometry (EV / LA / spray) is a batter-side property; the pitcher identity is already baked into which pitches reach contact. Spray must use `pull_relative_spray_angle` (SIM-051) so pull is always positive — see §3.1. |
| **Situation** (SIM-070, KDTree) | *nothing* | The situation *is* the filter — the 11-dim game state is the query. No tiling; the situation engine stays a single in-memory KDTree. Listed here only to state explicitly that it is **not** part of the play-pool tiling scheme. |

**Pool sizing floor.** A tile with fewer than `MIN_TILE_ROWS = 50` outcome rows is
**not** materialized on its own; its rows fall forward to the league-average
fall-back tile for that `bat_hand` (`<bat_hand>.faiss` at the season root with
`pitcher_id = 0` sentinel). This mirrors the SIM-051 batted-ball fall-forward and the
empirical-Bayes shrinkage philosophy: never sample from a pool too small to be
reliable. The sampler resolves a missing/too-small specific tile to this fall-back
automatically (§6.2).

### 3.1 Spray-angle column discipline (carried from SIM-051)

The batted-ball fingerprint's third dimension is spray. The build job MUST prefer
`pull_relative_spray_angle` and fall back to raw `spray_angle` with an INFO log when
the column is absent (older data). This is the exact `_select_spray_column()` contract
from the batted-ball engine — the cache builder reuses that helper rather than
re-implementing it, so the fall-back path is never collapsed.

## 4. Sub-index materialization (disk layout)

### 4.1 Directory layout

```
${BASEBALL_PLAY_POOL_DIR:-/data/play_pool}/
  <season>/
    <pitcher_id>/
      L.faiss            # pitch tile: pitcher vs LHB,  FAISS IndexFlatL2 (10-dim)
      L.faiss.meta       # JSON sidecar (see §4.3)
      L.rowids.npy       # int64 array, FAISS vector i -> sim.pitch_pool row id
      R.faiss            # pitcher vs RHB
      R.faiss.meta
      R.rowids.npy
    0/                   # pitcher_id == 0 sentinel = league-average fall-back tiles
      L.faiss  L.faiss.meta  L.rowids.npy
      R.faiss  R.faiss.meta  R.rowids.npy
    battedball/
      L.faiss            # batted-ball tile: LHB,  FAISS IndexFlatL2 (3-dim)
      L.faiss.meta
      L.rowids.npy
      R.faiss
      R.faiss.meta
      R.rowids.npy
```

`bat_hand` is encoded as a single uppercase character (`L` / `R`). Switch hitters are
resolved to the hand they batted with **for that PA** at fingerprint-build time using
`bat_hand` (never the roster `bats` value) — consistent with HANDOFF §4 and the
SIM-051 switch-hitter handling. There is no `S` tile.

### 4.2 Index type

Phase 3 ships **`IndexFlatL2`** for every tile. Rationale: tiles are small after
pre-filtering (typ. 200–5,000 vectors), flat L2 is exact, has zero training cost, is
trivially memory-mappable, and matches the FAISS L2 choice already locked for both
geometric engines (HANDOFF §1). IVF/HNSW are explicitly **deferred** to a Performance
Engineer ticket — the pre-filter already does the coarse partitioning that IVF would
otherwise provide. (SIM-281 records this as an open follow-up.)

Distances stay raw L2 — **engines emit distance, the sampler converts distance→weight**
(HANDOFF §4 "Engine score normalization"). The tile stores no weights.

### 4.3 `.meta` sidecar (JSON)

Written next to every `.faiss` file. Drives idempotent rebuilds (§4.4) and the RAM
accounting (§7):

```json
{
  "schema_version": 1,
  "pool": "pitch",                     // "pitch" | "battedball"
  "season": 2024,
  "pitcher_id": 477132,                // 0 for fall-back tiles; absent for battedball
  "bat_hand": "L",
  "dim": 10,                           // 10 for pitch, 3 for battedball
  "n_vectors": 1843,                   // includes recency duplicates
  "n_source_rows": 1421,               // distinct outcome rows before recency dup
  "recency_boost": true,
  "recency_boost_seasons": 2,
  "spray_column": "pull_relative_spray_angle",  // battedball only; or "spray_angle"
  "source_max_updated_at": "2026-05-19T07:14:55Z", // freshness watermark, see §4.4
  "build_timestamp": "2026-05-20T08:02:11Z",
  "builder_version": "sim301.1",
  "bytes_on_disk": 73720
}
```

### 4.4 Idempotency & staleness (the "rebuild only stale or missing" criterion)

A tile is **stale** and must be rebuilt iff any of:

1. The `.faiss`, `.meta`, or `.rowids.npy` file is missing.
2. `meta.source_max_updated_at` is older than the current
   `MAX(updated_at)` of the source rows that fall in the tile (i.e. new data landed).
3. `meta.builder_version` differs from the running builder's version (logic changed).
4. `meta.recency_boost` / `recency_boost_seasons` differ from the requested build
   flags (the boost policy changed — forces re-duplication, see §5).

Otherwise the tile is **fresh** and skipped. The serializer computes the per-tile
`source_max_updated_at` in one grouped DuckDB query up front, so a nightly no-op run
(no new data) touches zero `.faiss` files and costs one aggregate query per pool.
Writes are atomic: build to `*.faiss.tmp` / `*.meta.tmp`, `fsync`, then `os.replace`,
so a crashed build never leaves a half-written tile that looks fresh.

## 5. Recency lifecycle

The recency boost duplicates each outcome row whose `season` is within the most recent
`RECENCY_BOOST_SEASONS` (= 2) of the *build season set* exactly once, before adding
vectors to the FAISS index. Net effect: a 2024 pitch in a tile built for the
2017-2024 pool appears twice, a 2019 pitch once — recent form is ~2× as likely to be
sampled, matching the ML Engineer's recency-weighting strategy (agent_team.md:
"2× weight on last 2 seasons").

Lifecycle rules:

- **Determinism switch.** Production builds with `recency_boost=True`. Test/backtest
  builds pass `recency_boost=False` for reproducible nearest-neighbour ordering
  (mirrors the engines' existing behaviour).
- **Refresh cadence.** Because the boost is materialized *into* the tile, the set of
  "recent" seasons only changes at a season rollover. The nightly job therefore
  recomputes the boost **only** when (a) a tile is otherwise stale (§4.4), or (b) the
  calendar season advanced since `meta.build_timestamp` — condition (4) in §4.4 makes
  this automatic by treating a changed `recency_boost_seasons` window as stale.
- **In-season hot reload.** Within a season, newly ingested games for the current
  season make the relevant tiles stale via watermark (§4.4 rule 2); the nightly job
  rebuilds just those. `PlayPoolSampler.reload_recent()` (§6) lets a long-running
  simulation process pick up the rebuilt current-season tiles **without a full
  restart** — it re-stats the current-season tiles' `.meta` and reloads any whose
  `build_timestamp` advanced.

## 6. The `PlayPoolSampler` API (SIM-302)

`simulation/play_pool_sampler.py`. The four methods the Phase 4 loop and the SIM-220
backtester both call. The sampler is the **only** component that converts FAISS
distance → sampling weight, keeping the engines distance-pure (HANDOFF §4).

### 6.1 Construction

```python
PlayPoolSampler(
    pool_dir: str | os.PathLike = env("BASEBALL_PLAY_POOL_DIR", "/data/play_pool"),
    duckdb_path: str | os.PathLike = env("BASEBALL_DUCKDB_PATH"),
    *,
    max_resident_tiles: int = 256,     # LRU cap, enforces the RAM budget (§7)
    rng: numpy.random.Generator | None = None,   # injectable for deterministic tests
)
```

The sampler holds an LRU cache of loaded tiles (FAISS index + rowids + meta) and a
read-only DuckDB connection for fetching outcome payloads. `rng` is injectable so
tests get reproducible draws.

### 6.2 Methods

```python
def load_tile(self, pool: str, season: int, bat_hand: str,
              pitcher_id: int | None = None) -> TileHandle
```
Resolves and memory-maps the tile for the key, inserting it into the LRU (evicting the
least-recently-used tile if at `max_resident_tiles`). Fall-back resolution: if the
specific `(season, pitcher_id, bat_hand)` pitch tile is missing or its
`meta.n_source_rows < MIN_TILE_ROWS`, transparently resolve to the `pitcher_id = 0`
fall-back tile for that `(season, bat_hand)`. Idempotent — repeated calls return the
cached handle. Returns a `TileHandle` (index, rowids, meta).

```python
def sample_pitch(self, pitcher_id: int, bat_hand: str, season: int,
                 query_vec: numpy.ndarray, *, k: int = 25) -> dict
```
k-NN search the pitch tile with the 10-dim `query_vec`, convert the k distances to
weights via `w_i = 1 / (d_i + EPS)` (EPS = 1e-6), normalize, draw **one** neighbour
with `rng.choice(p=weights)`, fetch its outcome row from `sim.pitch_pool`, and return:
```python
{"row_id": int, "pitch_outcome": str, "distance": float,
 "weight": float, "tile": "<season>/<pitcher_id>/<bat_hand>", "fellback": bool}
```
`fellback` is True when the fall-back tile served the request. `k` is clamped to the
tile's `n_vectors`.

```python
def sample_batted_ball(self, bat_hand: str, season: int,
                       query_vec: numpy.ndarray, *, k: int = 25,
                       return_distribution: bool = False) -> dict
```
Same shape, against the 3-dim batted-ball tile. When `return_distribution=True`,
instead of drawing one row it returns the **outcome distribution** over the k
neighbours — a probability dict keyed by event type
(`{"single": 0.31, "double": 0.08, "out": 0.55, ...}`) computed from the normalized
distance weights. This is the form the prop-betting / backtesting path consumes
(it wants the full distribution, not a single draw).

```python
def reload_recent(self, current_season: int) -> int
```
Re-stats every resident tile whose `meta.season == current_season`; for any whose
on-disk `build_timestamp` is newer than the resident copy, evict + reload. Returns the
number of tiles reloaded. Lets a long-lived sim worker pick up nightly current-season
rebuilds without restart (§5).

### 6.3 Invariants the SIM-302 unit tests must lock

Built against synthetic 1k-row tiles (no DuckDB-live dependency, per the project's
`__new__`/in-memory test pattern):

1. `sample_pitch` / `sample_batted_ball` return a row that is actually in the tile.
2. Zero-distance query (query == an indexed vector) puts dominant weight on that
   vector (nearest-neighbour sanity).
3. With a fixed `rng` seed, draws are reproducible.
4. `return_distribution=True` yields a dict that sums to 1.0 (± 1e-9) over a closed
   event vocabulary.
5. Missing specific tile → fall-back tile served, `fellback is True`.
6. LRU eviction never exceeds `max_resident_tiles` resident indexes.
7. `k > n_vectors` is clamped, never raises.

## 7. Performance & RAM budget

**Hard cap: total resident play-pool + FAISS memory ≤ 2 GB regardless of worker
count** (the SIM-114 envelope). This is the constraint SIM-280 quantifies and SIM-281
turns into a parallelism decision; SIM-300 states the contract the cache + sampler
must honour:

- **Flat L2, float32.** A pitch tile of `n` vectors costs `n × 10 × 4` bytes (+ small
  FAISS overhead) for the index and `n × 8` bytes for rowids. A 5,000-vector tile is
  ~240 KB. Batted-ball tiles (3-dim) are smaller. Tiles are mmap-friendly.
- **LRU residency, not load-everything.** The sampler never loads the whole pool. With
  `max_resident_tiles` capping resident tiles, peak tile RAM is bounded by
  `max_resident_tiles × max_tile_bytes`. At 256 tiles × ~256 KB that is ~64 MB of tile
  data per process — leaving headroom for the engines under 2 GB.
- **Shared, not per-worker, where possible.** Tiles are read-only after build, so the
  Phase 4 parallelism model (SIM-281) should attach them via
  `multiprocessing.shared_memory` / mmap so N workers share one resident copy rather
  than N copies. SIM-300 only requires that tiles be serialized in an mmap-able,
  process-shareable form (they are — flat FAISS + `.npy`); SIM-281 picks the sharing
  mechanism.
- **Build-side memory.** The serializer streams per-tile from DuckDB
  (`GROUP BY pitcher_id, bat_hand`) and builds one tile at a time, so the nightly job's
  own footprint is one tile + one result batch, not the whole pool.
