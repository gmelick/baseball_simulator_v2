# SIM-486 — Retire the per-tile fallback path: the full change list

*Prepared 2026-09-04. APPLIED 2026-09-06 (option 1, in full). Every line number below is
against the working tree at commit 27e6953 plus the uncommitted SIM-520/522 edits, i.e. the
tree BEFORE the change. What differed from the plan, in practice:*

* *The loader-side builder-version check (§5.1) was not added: the loader's own unit tests
  build partial bundles on purpose. The guard sits at the draw instead —
  `FullPoolSampler.battedball_new_pa` and `StateMachine._full_pool_fielding` raise on a
  pool without transition columns.*
* *The synthetic bundle carries optional advancement pools (`league_artifacts`) so the no-DB
  run environment stays realistic (~4.8 R/team-game); fixed-play bundles omit them so a
  single-play test is deterministic.*
* *`test_qa_sim325`'s baked reference distribution still passes its chi-squared gate against
  the new harness, so it was not re-baked. Two harness tests gained per-test timeout marks
  (the synthetic games cost ~30 ms each; the old resolver games ~1 ms).*
* *The `green_light_rate` deletion stays with SIM-427 (§5.2), as planned.*
* *Two production defects surfaced once the no-DB games became realistic, and were fixed:
  the play recorder kept the live `GameState` as every play's `next_state` (the replay
  card, decisions and per-pitch snapshots were built from the final state alone), and the
  linescore attributed a third-out play's runs to the next half-inning. See CHANGES.md.*

## 1. What the ticket asks, and what the tree actually contains

The 2026-08-10 filing (`docs/audit/2026-08-10-sim-loop-remediation-tickets.md` §SIM-486)
says: delete `PlayResolver`, the fingerprint stubs, `PlateAppearanceSimulator` and the
`SIM_FULL_POOL` flag, so the tests run the production path because it is the only path.

The per-tile path is larger than those four names. It is a second simulator that shares
the count machine with production and nothing else:

| Layer | Per-tile (to delete) | Production (stays) |
|---|---|---|
| Nightly build | `pipeline/batch/play_pool_cache.py` writes FAISS tiles + 4 norm/centroid JSON files | `pipeline/batch/engine_artifacts.py` writes the bundle |
| Read side | `simulation/play_pool_sampler.py` (`PlayPoolSampler`, k-NN over tiles) | `simulation/full_pool_sampler.py` |
| Query vector | `simulation/fingerprints.py` + `matchup_provider.py` + `score_fusion.py` | none (the pool is scored whole) |
| Loop glue | `PlateAppearanceSimulator`, `PlayResolver`, the `sampler` / `k` / `fingerprint_deriver` / `resolver` / `sim` constructor seams, the `else` branches in `step_pitch` and `_resolve_in_play` | `_full_pool_outcome`, `_full_pool_fielding`, `_resolve_in_play_transition` |
| Factory | `_SAMPLER_BUILDER`, `_DERIVER_BUILDER`, `_attach_shared_tiles`, `GameSpec.shared_segments` | `_build_full_pool_sampler` + the SIM-403b shared views |
| Switch | `SIM_FULL_POOL` (compose, `api/main.py`, `tests/conftest.py`, the `_full_pool` sim-kwarg) | — |

Three facts change how to read the ticket's two dependencies:

1. **Production has not run the per-tile path since 2026-06.** `SIM_FULL_POOL=1` is
   pinned in compose. The fallback fires only when the artifact bundle is missing or
   corrupt, and then it silently serves a different simulator. Deleting it turns that
   silent degradation into a loud boot failure. That is better, and it does not wait on
   SIM-467: the speed reason in the filing was moot the day the flag went to 1.
2. **The nightly chain builds the dead path and never builds the live one.**
   `scripts/nightly_ingest.sh` step 3/3 runs `play_pool_cache` (tiles nobody reads);
   nothing in the Makefile, the compose file or the Ofelia job runs
   `pipeline.batch.engine_artifacts`. The bundle the production sampler reads is rebuilt
   by hand only. SIM-486 should fix the chain, not just delete a step.
3. **The unit suite has no production in-play path without a bundle.** Twelve test
   modules, the batch runner's no-DB factory and the chi-squared replay harness resolve
   contact through an injected `PlayResolver`. Their signals carry no transition, so they
   run the LEGACY advancement branch (`_advance_runners`, `_extra_advance`,
   `_full_pool_out_advancement`, the 0.92 / 0.45 / 0.30 constants) that production has
   not run since the SIM-511 transition draw landed on 2026-08-19. That branch is the
   divergence the ticket exists to remove, and it is not on the filing's list. §4 is the
   one design decision the owner must make.

**Recommendation:** start SIM-486 now. SIM-450's lane exists and certifies; SIM-467 is
not a real prerequisite.

## 4. The design decision: what replaces the injected resolver

The filing says tests run the production path because it is the only path. Today the
production in-play path needs a `FullPoolSampler`, and the legacy path exists so a test
can resolve contact without one. Two ways out:

**Option 1 (recommended) — one in-play path; the test seam supplies rows in the
production shape.** `_resolve_in_play_transition` already tolerates a missing sampler:
`_run_advancement_draws` returns station-to-station when `full_pool_sampler is None or
not fp.has_advancement()` (`sim_loop.py:1920-1921`). So a no-DB test can drive the
PRODUCTION in-play path if its `FieldingSignal` carries a `transition` dict. Concretely:

* Add one shared builder module, `simulation/synthetic_bundle.py`, that returns an
  in-memory `EngineArtifacts` (a `HandPool` with one row per count bucket × outcome, a
  `BattedBallPool` with the SIM-511 transition columns, optional steal / advancement
  pools). `test_sim498_rng_streams.py:66-112` and `test_sim511_512_transition_draw.py`
  already build exactly this by hand, per file. Parameters: the event mix (so `sim324`'s
  league rates become row multiplicity or recency weight), the hit rate (so
  `_CyclingResolver(hit_rate=0.30)` becomes a pool), and the seed.
* `rng_driven_machine_factory` builds `StateMachine(FullPoolSampler(synthetic_bundle()))`.
  It stays a module-level dotted-ref factory, so every API / integration / bench consumer
  is untouched. `_CyclingResolver` and `_RngOutcomeStateMachine` are deleted.
* `replay_chi_squared._LeagueInPlayResolver` and `_LeagueOutcomeMachine` become a
  synthetic bundle whose rows carry `LEAGUE_PITCH_MODEL` / `LEAGUE_INPLAY_MODEL` as weights.
* The twelve test modules re-express each scenario as pool rows. `sim319` / `sim499` /
  `sim365` inject one fixed row per test (a single, a double play, an error); the
  full-game harnesses (`sim320` / `sim323` / `sim326` / `sim349`) take the default mix.
* The module lives in `simulation/`, not `tests/`, because the batch runner's factory
  must import it by dotted reference in a worker process. The precedent is
  `rng_driven_machine_factory` itself, which `api/routes/games.py:42` documents as the
  no-DB seam.

Then delete the `resolver` parameter, `PlayResolver`, and the legacy in-play block (§5.1).
Cost: the twelve migrations, roughly a day. Benefit: the unit suite exercises the same
advancement model users get, which is the ticket's stated purpose.

**Option 2 — keep a duck-typed `resolver` seam (a `Protocol`, no default class) and keep
the legacy advancement block for resolver-supplied signals.** Smaller, but the divergence
survives: tests keep certifying an advancement model that production never runs.
Rejected.

Two smaller seams go with option 1 and need a ruling only if option 2 is chosen:

* `resolver.dropped_third_strike` (`sim_loop.py:2811`): since SIM-517 the production
  signal is `_last_pitch_got_away`. Tests set that attribute instead.
* `resolver.resolve_steal` (`sim_loop.py:3555`): tests already use `stage_steal()`.
